# Дизайн: удалённое редактирование плантации (без GPS-присутствия)

## Контекст

Сейчас единственный edit-флоу плантации (`EditPage`, `edit_vm.dart`) требует GPS-подтверждение
физического присутствия на участке для **любого** изменения — включая чисто административные
данные (субсидии, инвестиции, договоры), которые не требуют осмотра земли.

`EditVM.editPlantation()` (`edit_vm.dart:983-1029`) на каждый сабмит:
1. Запрашивает GPS (`_currentUserLocation()`).
2. Fail-closed проверяет расстояние до полигона плантации (`_checkLocationLimit()`) — блокирует
   сохранение, если GPS недоступен или юзер далеко.
3. Только после этого строит и шлёт PATCH.

Это правильно для физических данных (площадь, тип земли, фото — требуют осмотра участка), но
избыточно для административных данных, которые сотрудник может и должен уметь редактировать из
офиса — например, добавить сведения о полученной субсидии сразу после того, как узнал о ней, не
выезжая на плантацию.

## Цель

Разделить редактирование на два независимых флоу:
- **«Tahrirlash (joyida)»** — как сейчас, вся форма, GPS обязателен fail-closed.
- **«Tahrirlash (masofadan)»** — новый, только административные поля, без GPS-запроса и без
  antifraud-проверки вообще.

## Разделение полей

**Только «joyida» (физические, требуют осмотра участка):**
- `land_type` (тип земли)
- `empty_area`, `not_usable_area` (площади)
- `fruit_areas`, `types`/`plantation_type` (состав насаждений)
- фото плантации

**«Masofadan» (административные, не требуют присутствия):**
- `subsidies` (субсидии)
- `investments` (инвестиции: местные/зарубежные)
- `irrigation_area`, `irrigation_systems_count` (орошение/tomchi)
- `trellises` (шпалеры)
- `reservoirs` (резервуары)
- `garden_established_year` (год основания)
- `kontur_number`
- `fertility_score`, `is_fertile`

## Подход

**Один `EditVM`, два экрана.** Не дублируем VM — `EditRemotePage` (новый) и `EditPage`
(существующий, без изменений) оба читают/пишут один и тот же `EditVM` provider. `EditRemotePage`
рендерит подмножество уже существующих виджетов формы (subsidiya/investment/tomchi/trellis/
reservoir/year/kontur секции — переиспользуются как есть, вырезаны только площадь/тип
земли/фото секции).

**Новый VM-метод `editPlantationRemote()`** — копия `editPlantation()` без шагов 1-2 (GPS-запрос
и `_checkLocationLimit`). Строит тот же `_buildPatchBody()`, шлёт PATCH сразу. `user_location` в
тело не добавляется (нет собранной точки).

**Точка входа**: на `plantation_view_page.dart` (`_buildActionButtons`, ~строка 1461) вместо
одной кнопки «Tahrirlash» — две отдельные кнопки рядом: «Tahrirlash (joyida)» (ведёт на
существующий `editPage`-роут) и «Tahrirlash (masofadan)» (новый роут на `EditRemotePage`).

**Как юзер понимает разницу** — без объяснения два похожих пункта меню неотличимы, юзер не
знает заранее какие поля где. Каждая кнопка получает короткий subtitle прямо под лейблом,
поясняющий её охват:
- «Tahrirlash (joyida)» — subtitle: «Maydon, tur, rasmlar — joyida turib to'ldiriladi»
- «Tahrirlash (masofadan)» — subtitle: «Subsidiya, investitsiya va h.k. — istalgan joydan»

Если юзер всё равно откроет не тот экран и не найдёт нужное поле — это не тупик: нужное поле
просто отсутствует в этой форме, он закрывает экран и открывает другой (не блокирующая ошибка,
не потеря данных — оба экрана читают/пишут один и тот же `EditVM`/бэкенд-состояние).

**Бэкенд**: без изменений. `user_location` в PATCH уже опционален (не всегда шлётся и сейчас,
если GPS недоступен) — сервер не проверяет присутствие сам, это чисто клиентское ограничение
(как и весь остальной antifraud в проекте). Achievable ограничение: юзер физически не может
попасть в `EditRemotePage` виджеты для площади/фото — тех виджетов там просто нет в дереве.

## Верификация
- `flutter analyze` после каждого изменения.
- Ручная проверка: на `EditRemotePage` сохранение проходит без запроса геолокации/разрешений,
  даже в airplane mode.
- Ручная проверка: `EditPage` (joyida) продолжает блокировать сохранение при GPS вне радиуса —
  regression на существующий antifraud.
- Проверить, что оба экрана, редактируя один и тот же `EditVM`, не конфликтуют при последовательном
  открытии (например: открыл remote, сохранил, потом открыл joyida того же id — детейлы должны
  перезагрузиться заново, не унаследовать stale VM-state).
